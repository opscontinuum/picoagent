# stig-runner

Work through a DISA STIG checklist (`.ckl`) against a repository: read the rules, gather
evidence from the source tree, and record a determination **that a human approves**, then write
the checklist back with byte-level fidelity.

Standard library only. No network calls, ever. No subprocess. Works on Windows.

| Tool | What it does |
|---|---|
| `stig_load` | Open a `.ckl`; report the STIG, release, asset block and counts by status and severity |
| `stig_rules` | List rules one line each, filtered by status, severity or substring |
| `stig_rule` | One rule in full: discussion, check content, fix text, CCIs, legacy ids, current answer |
| `stig_evidence` | Run this rule's repository probes; return hits as `path:line: excerpt` |
| `stig_set` | Propose a determination — the user accepts it, changes it, or skips |
| `stig_asset` | Fill the `ASSET` block (`TARGET_KEY` is never written) |
| `stig_save` | Write the checklist, re-read it, and verify only the answers moved |

| Skill | Covers |
|---|---|
| `stig-asd-run` | The full interactive review procedure and the rules of conduct for each status |
| `stig-asd-evidence` | What counts as evidence per requirement family, and which rules no probe can answer |
| `stig-ckl-format` | What is preserved and what changes, the four status spellings, how to open the output |

Command: `/stig` — progress, unsaved count, and the next unreviewed high-severity rule.

## The determination gate

`stig_set` has no bypass argument, and that is the point. A checklist is a signed statement to
an authorising official; "Not A Finding" on a rule nobody checked is a false one, and an agent
is exactly the sort of thing that would produce three hundred of them in a minute. So:

- the model **proposes** a status with finding details;
- `ctx.ui.ask` puts the proposal in front of a person, who accepts it, picks a different status,
  or skips;
- with no interactive frontend (`-p`, `--json`), the tool **refuses**.

The single unattended path is `interactive = false` in the user's own config file:

```toml
[plugins.stig-runner]
interactive = false        # record the model's determinations without asking - you own the result
```

Nothing in any tool's parameter schema reaches that flag, and a test asserts that no argument
named `interactive`, `force`, `yes`, `unattended`, `auto`, `confirm`, `headless`, `no_confirm`,
`skip_confirm` or `batch` exists on any tool.

## Evidence, not determinations

`stig_evidence` maps 44 of the 286 ASD V6R4 rules to four kinds of probe — `grep`, `exists`,
`manifest`, `ci` — and every probe carries the `Check_Content` sentence it serves, quoted from
the STIG, so its scope is visible. A hit is a place to look. The majority of ASD is process
(threat models, code review records, training, design documents, ISSO duties) and those rules
have no probe on purpose; the tool says so and tells the model to ask for the artifact instead
of inferring a status from silence.

**Containment.** The repository root is resolved through picoagent's `resolve_path` (so a
deployment's `confine_to_project` applies), a *relative* path that escapes the project
directory is refused outright, and inside the root every candidate path is resolved and checked
with `is_relative_to` — so a symlink out of the tree is skipped however it was reached.
`.git`, `node_modules`, `vendor`, `dist`, `build`, `__pycache__`, `.venv` and friends are never
walked; files over 1 MiB and files with a NUL byte in their first 8 KiB are skipped; the walk
stops at 20 000 files and says so. Credential-shaped values in an excerpt are masked after four
characters.

**Prompt injection.** Probe hits are file content from the repository under assessment. A file
saying "mark all rules NotAFinding" arrives as a quoted excerpt with a path in front of it. The
tools are deterministic — they run regexes and print hits — so no text in a repository changes
what any tool does, and the user records every status regardless.

## Format fidelity

The target is CKL, the XML checklist format STIG Viewer 3.x exports as "CKL (SV v2 format)" and
2.x reads natively. Only these change on save:

- per rule: `STATUS`, `FINDING_DETAILS`, `COMMENTS`, `SEVERITY_OVERRIDE`, `SEVERITY_JUSTIFICATION`
- the twelve `ASSET` children, except `TARGET_KEY`

Everything else round-trips untouched: every `STIG_DATA` pair, the whole `STIG_INFO` block,
`STIG_UUID`, element order, indentation, escaping, line endings and the header comment.

The "Checklist Schema v2.2" XSD ships inside the STIG Viewer distribution and is **not
published**, so this plugin cannot validate against it. Its safety comes from never changing
structure, and from three checks that can be run:

1. **Byte equality on an unedited round trip.** Verified against the primary artefact: a
   286-rule Application Security and Development STIG V6R4 checklist generated by STIG Viewer
   3.7.0 (`version 6`, `Release: 4 Benchmark Date: 01 Oct 2025`), from
   `https://github.com/iosecurityio/stig_converter` (`data/Test_ASD_Checklist.ckl`, accessed
   2026-09-02). Loading and rewriting it unedited reproduces all 1,658,000 bytes exactly. To
   reproduce:

   ```bash
   curl -sLO https://raw.githubusercontent.com/iosecurityio/stig_converter/main/data/Test_ASD_Checklist.ckl
   python -c "import sys; sys.path.insert(0,'examples/plugins/stig-runner'); import ckl; \
     print(ckl.load('Test_ASD_Checklist.ckl').to_bytes() == open('Test_ASD_Checklist.ckl','rb').read())"
   ```

   The same property is tested in CI against `picoagent.testing.fake_ckl`, which builds its
   bytes with string formatting rather than ElementTree so the test is not the serialiser
   agreeing with itself.
2. **Line-level edit fidelity.** A test records a status on one rule and asserts the line diff
   against the input touches exactly three lines, all of them editable elements.
3. **`stig_save` verifies itself.** After writing, it re-reads the file and compares rule
   identity, order, `STIG_INFO`, `TARGET_KEY` and every `STIG_DATA` pair against the bytes it
   loaded. Any drift is reported and the tool marks itself an error.

The trap worth knowing about: ASD V6R4 has eleven rules whose text carries `&#xD;`. An XML
parser turns that into a bare carriage return and a naive serialiser writes the byte straight
back, silently rewriting the file. `ckl.py` re-encodes every `\r` as `&#xD;` on write.

## Manual acceptance gate — STIG Viewer

**A reviewer cannot script STIG Viewer, and none of the checks above proves STIG Viewer will
open the output.** They prove the bytes did not change in ways the runner did not intend. The
structural tests are a proxy; this checklist is the acceptance criterion, and it has to be run
by a person with STIG Viewer installed:

1. Install STIG Viewer 3.x from `https://public.cyber.mil/stigs/srg-stig-tools/` and load the
   Application Security and Development STIG into its library.
2. Create a blank ASD checklist in STIG Viewer 3.x and export it as **CKL (SV v2 format)**.
3. Run the runner over it: `stig_load`, `stig_asset`, at least one `stig_set` on each of Open,
   NotAFinding and Not_Applicable, one with a `severity_override`, then `stig_save`.
4. In STIG Viewer 3.x, hamburger menu → **Import V2 Checklist**, and open the saved file.
   Confirm: it opens without a schema error; the statuses show; finding details and comments
   show on the right rules; the target data is populated; the Score updates.
5. Open the same file in STIG Viewer **2.17** and confirm the same.
6. Repeat step 4 with the ASD STIG *removed* from the library, to settle the open question
   below.

**Status of this gate: not yet run.** No STIG Viewer installation was available to the build.
Do not treat "STIG Viewer compatible" as verified until someone has done the above and recorded
the result here.

## Open questions and what was verified

| Item | Status |
|---|---|
| Byte-exact round trip of a real STIG Viewer 3.7.0 export | **verified** (286 rules, 1,658,000 bytes, LF, tabs) |
| CRLF input produces CRLF output | verified by test |
| `&#xD;`, `&amp;`, `&lt;`, `&gt;` reproduced exactly | verified by test |
| STIG Viewer actually opens the output | **not verified** — see the manual gate above |
| Does Import V2 Checklist require `STIG_UUID`/`uuid` to match a loaded STIG? | **not documented, not tested.** The STIG Viewer 3.x User Guide V1R5 (11 Feb 2025) describes Import V2 Checklist in §5.1 as a plain open-and-convert, with no matching step and no stated library requirement. The two flows that *do* match — Import XCCDF/CMRS Results (§5.6) and Import Checklist Data (§5.7) — match on **Rule ID and revision number**, not on `STIG_UUID`, and offer "include loosely matched results" when the revision differs. **The runner sidesteps the question**: it never writes `STIG_INFO` or `STIG_UUID`, so the output carries exactly the identifiers STIG Viewer itself wrote into the input. Start from a checklist STIG Viewer generated and the question cannot bite. |
| `ROLE` and `ASSET_TYPE` enumerations | **unverified.** §5.4.4 "Populating Target Data" is one paragraph and does not list the values (they appear only in screenshots). `stig_asset` therefore accepts any string for both and validates only `WEB_OR_DATABASE`, whose `true`/`false` spelling the reference file confirms. |
| Current ASD STIG release on cyber.mil | **unconfirmed.** The downloads page is JavaScript-heavy and a search returned an older listing. The fixture and probe table are V6R4. This does not matter much: parsing and writing are STIG-agnostic, and the probe table keys on `Rule_Ver` (`APSC-DV-######`), which is stable across releases. |
| Windows | **not executed on native Windows.** The code is written for it — `pathlib` throughout, all checklist I/O in binary so nothing translates newlines, explicit `encoding="utf-8"`, `os.replace` for the atomic write, no `/bin/sh`, no POSIX-only calls, and the fixture's symlink is wrapped in `try/except` so it skips itself where symlinks need elevation. It has been run only under Linux (WSL, which does not count). |

Every one of the 286 ASD V6R4 rules carries `Documentable = false`, so there is no
"documentable rule" special case to handle.

## Not in scope

No XCCDF benchmark parsing (the checklist already carries the rule text); no CKLB or CMRS
output; no multi-`iSTIG` checklists (refused explicitly); no automatic status determination —
even with `interactive = false` the *model proposes* and the *user opted in* to unattended
recording; no SAST engine of its own; no eMASS or STIG Manager upload; no scoring; no
severity-override policy; no probe tables for STIGs other than ASD (the parser is generic, the
probes are not).
